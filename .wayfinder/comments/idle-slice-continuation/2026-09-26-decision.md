# Decision: how a halted parse continues on the Lisp thread

2026-09-26. **Self-adopted; the user confirmed it on 2026-09-26.**

Evidence: the [halt and resume contract](../ts-halt-resume-contract/2026-09-25-resolution.md),
the [display policy](../pending-parse-display-policy/2026-09-26-decision.md),
the [latency baseline](../../research/ts-latency-baseline.md), and nemesis
`21e6107d76c`:
- After any timer runs, `wait_reading_process_output` redisplays and checks
  timers again until input arrives (`src/process.c:5534-5545`).
- `jit-lock-stealth-fontify` re-fires an idle timer within one idle period
  with `timer-inc-time` and `timer-activate-when-idle` with DONT-WAIT
  (`lisp/jit-lock.el`, stealth section).

## Decisions

1. **Slices run from one Lisp idle timer.** The timer is armed when a
   budgeted attempt halts, with DONT-WAIT so that it fires at once if
   Emacs is already idle. Each firing re-arms itself with the jit-lock
   stealth pattern while any parse is pending. Rejected alternatives:
   - A hook between `read_socket` polls in `keyboard.c`. It adds sync
     surface in a hot upstream file.
   - A plain repeating timer. It would also fire during commands.
2. **Slice length equals the budget, 2 ms to start with.** One firing
   runs slices back to back until the parse finishes or
   `input-pending-p` is true, checking input between slices. Input
   therefore waits at most one slice. Idle time is otherwise spent
   finishing the parse as fast as a synchronous parse would. The progress
   callback only compares the clock. It never checks input, quits or
   calls Lisp, as the contract requires. The C primitive continues one
   parser for one budget and returns whether it finished. Its name and
   location belong to ticket 24.
3. **An edit during a halted parse resets and restarts.** The edit calls
   `ts_parser_reset` (the contract requires this), and the halted work is
   discarded. The next budgeted attempt parses from the edited old tree.
   Finishing synchronously at the edit would put the whole parse back on
   the keystroke, which is the cost this map removes.
4. **Redisplay starts parses, but never continues one.**
   `treesit--pre-redisplay` makes a budgeted attempt only when an edit
   came after the last attempt. A pending parse with no new edit is left
   to the idle slices. So a redisplay adds at most one budget, and only
   after an edit. Cursor motion and scrolling add nothing.
5. **A staleness deadline bounds starvation.** Under continuous typing,
   each edit restarts the parse, and idle gaps may be shorter than the
   parse. The quote case in the 800 KB file needs 63 ms. If a buffer has
   had an unfinished parse for longer than the deadline (0.5 s to start
   with), its next budgeted attempt runs without a budget. The age
   counts from the first halt since the last completed tree, and restarts
   do not reset it. The worst case becomes one full-parse hitch per
   deadline with faces stale for at most about the deadline. Today it
   is one hitch per keystroke. Waiters finish the parse anyway (display
   policy, decision 4).
6. **Completion is handled by what already exists.** When a slice
   finishes the parse, the parser's notifiers mark the changed ranges.
   The slice then clears the buffer's `fontified 'defer` marks (display
   policy, decision 7) without forcing a redisplay. When the timer
   returns, the input wait redisplays, and the string face appears. No
   explicit `redisplay` call and no special event are needed.
7. **Several pending buffers are served most recently halted first.**
   Hidden buffers are served too, because idle time is free and a later
   waiter would otherwise pay. A pending parser leaves the list when its
   parse finishes, when it is deleted or its buffer is killed, or when a
   waiter finishes it. A change in narrowing resets it like an edit
   (`treesit_sync_visible_region`, per the contract).

## Numbers stage 2 must report (inputs for the gate, ticket 25)

- Restarts per pending parse, and the pending age at completion, under
  the latency scenarios and under a scripted burst of typing at 30 ms
  intervals.
- How often the staleness deadline fires.
- The largest single slice (giant tokens and end-of-file balancing can
  exceed the budget, per the contract).

The starting values (2 ms and 0.5 s) come from the frame budget and the
baseline. Their names, and whether they become `defcustom`s, stay in the
map's user-facing knobs fog until stage 2 measures them.
