# Progress: parse cap implemented, waiting for the user's live check

2026-09-26, branch `treesit-stage2` (off `treesit-stage1`).

## What it does

- `treesit-budget-parse-limit` (default 2.0 s, nil for none) halts any
  parse, first or incremental, through the progress callback. The
  callback checks the clock on each call; tree-sitter keeps calling it
  inside the old TypeScript grammar's lexer loop (about 18,000 calls a
  second), so the hang does stop.
- A parser that halts gives up: it is reset and, until
  `treesit-budget-retry`, parses an empty input instead of its buffer
  (microseconds). A message names the buffer and the limit.
  `treesit-budget-gave-up-p` tells whether a parser gave up;
  `treesit-budget-stats` counts `:halts`.
- The retry drops the empty tree, so the next parse starts from
  scratch, and flushes font-lock in the buffer.
- Upstream hooks: see AGENTS.md. The NULL-tree path in
  `treesit_ensure_parsed` now clears `within_reparse` before signalling.

## Design change during implementation: no error on give-up

The first version kept the old tree and signalled `treesit-parse-error`
at every later parse. In a GUI run this printed an error from
`treesit--pre-redisplay` through `with-demoted-errors` into the echo
area at every keystroke, logged a jit-lock error per chunk, would have
made `syntax-ppss` fail through `treesit--pre-syntax-ppss`, and aborted
the major mode's setup ("File mode specification error") when the
first parse gave up. Parsing an empty input instead needs no change in
`treesit.el`: readers find an empty tree, fontification applies no
faces, and nothing signals.

## Gate results

- ERT: `treesit_budget-tests.el` 8/8 (three new: halt and give-up,
  retry equals a full parse and incremental parsing resumes, nodes of
  the dropped tree are outdated). `treesit-tests.el` 35 passed,
  5 skipped, as before.
- Batch, old grammar and `ts-grammar-hang.ts`: a limit of 0.1 s opens
  the file in `typescript-ts-mode` in 0.13 s, 0.5 s in 0.50 s.
- GUI, fresh process, old grammar: the file opens with the message and
  no errors; five edits with redisplay afterwards cost nothing. A reparse
  halt in a 200 KB Python file (limit 0) is also silent, and edits
  take under 1 ms each; after a retry the parser parses normally.
- Cost: 80 reparses of a 200 KB Python file take 1821-1842 ms without
  the limit and 1844-1845 ms with it, within noise. The latency
  scenarios (`ts-perf.el`), limit nil against 2.0, agree within about
  1% in every scenario (for example quote in large Python: median 66.4
  against 65.7 ms; open large TypeScript: 248 against 245 ms).
