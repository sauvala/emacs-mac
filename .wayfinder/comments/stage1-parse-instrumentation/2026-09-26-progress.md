## What was built

- `src/treesit_budget.c` parses through `ts_parser_parse_with_options`
  (ABI 15 and later) with a progress callback that never halts, and
  plain `ts_parser_parse` below ABI 15. MS-Windows loads tree-sitter
  dynamically, so there `treesit_budget_parse` is a macro for
  `ts_parser_parse` and the stats stay zero.
- `treesit-budget-stats` (optional RESET) returns a plist:
  - `:parses`, all parses;
  - `:first-parses`, `:first-seconds` and `:first-max-seconds`, for
    parses with no previous tree (file visits);
  - `:seconds`, `:max-seconds`, `:over-1ms`, `:over-3ms` and
    `:over-8ms`, for reparses only;
  - `:progress-calls`.

  First parses are kept apart because they stay synchronous in stage 2
  and would otherwise swamp the over-8 ms count.
- The hooks follow [Keep the change small in upstream files](../sync-surface-containment/2026-09-26-decision.md):
  one call in `treesit_ensure_parsed`, one line in `syms_of_treesit`,
  the declarations in `treesit.h` and the object in `Makefile.in`.
  `AGENTS.md` lists them. The parser struct field and the
  `treesit_delete_parser` line are left for stage 2, which first needs
  per-parser state.
- Tests: `test/src/treesit_budget-tests.el` (4 tests). Its name follows
  the test Makefile's rule, which maps `src/FOO-tests.el` to `src/FOO.c`.

  A batch full parse of 900 KB of Python takes 91-92 ms on both builds.
- **Measurement trap.** The first harness runs showed the first visit
  of each large file 300 ms slower on the branch. The cause is JIT
  native compilation, not parsing. A new DEFUN changes the build
  fingerprint (`32_0_50-efee7d74`), which has no user eln cache yet. The
  run then queues `native--compile-async` for `python.el` and others
  (614 calls in one visit), and exits before any `.eln` is written.
  nemesis's fingerprint had a cache from 2026-09-25. Compare builds
  with different fingerprints with
  `(setq native-comp-jit-compilation nil native-comp-eln-load-path (last native-comp-eln-load-path))`
  loaded before the harness.
